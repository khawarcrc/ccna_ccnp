LAB NAME

Lab 075 - Review Configuration Lab 3

==================================================
LAB OBJECTIVE
==================================================

A large cumulative review lab (the second-to-last lab in the series)
combining BGP, OSPF, EIGRP, GRE, and PPP across two independent
enterprises sharing the same ISP. Enterprise A (R1, R2) uses static
routing to reach the Internet and OSPF internally, plus a GRE tunnel
between its two branches. Enterprise B (R3, R4) uses EIGRP internally
and eBGP (rather than a simple static route) to reach the ISP over a
PPP link authenticated with CHAP. Finally, diagnose and fix a missing
route preventing PC1 (Enterprise A) from reaching PC4 (Enterprise B).

Note: unlike the earlier NAT labs, this lab's "Internet cloud" does NOT
simulate the real-world restriction against routing private (RFC 1918)
addresses over the Internet — no NAT or ACL workaround is needed here
to send private-addressed traffic across it.

Enterprise A: R1 and R2 each reach the Internet via a static default
route out their WAN interface (G0/0/0), and additionally run a GRE
tunnel directly between each other (Tunnel0, 192.168.12.0/30) riding on
top of that same Internet path — OSPF (area 0) runs between R1 and R2
over BOTH their LAN interfaces and the tunnel interface, letting them
exchange internal routes as if directly connected. Enterprise B: R3
connects to the ISP over a PPP serial link (203.0.113.8/30)
authenticated with CHAP, and additionally peers via eBGP (AS 65000 on
R3's side, AS 65001 on the ISP's side) rather than using a simple
static route. R3 and R4 run EIGRP (AS 100) internally.

Note: several exact subnet addresses in this lab (R2's LAN, the R3-R4
transit link) were not clearly distinguishable in the source captions
— reconstructed above from context (address patterns explicitly
confirmed elsewhere in the transcript, like 192.168.1.0/24 for PC1's
subnet and 192.168.3.0/24 for R3's LAN) rather than invented; verify
against the live Packet Tracer file if exact precision matters.

STEP 5 - ENTERPRISE B: CONFIGURE EIGRP BETWEEN R3 AND R4

Command                                    Explanation
-----------------------------------------------------------------------------------------

                                            neighbors — unlike OSPF's process ID.

STEP 6 - ENTERPRISE B: CONFIGURE eBGP ON R3 TOWARD THE ISP
==================================================

Rather than a static default route (the method used in Enterprise A),
Enterprise B connects to the ISP with BGP: R3 is in AS 65000, the ISP
is in AS 65001.

---------------- R3 ----------------

Command                                            Explanation
-----------------------------------------------------------------------------------------
router bgp 65000
 neighbor 203.0.113.9 remote-as 65001                Manually specifies the ISP as
                                                    a BGP neighbor, in its
                                                    separate AS — an eBGP
                                                    peering, same pattern as the
                                                    earlier BGP labs.
 network 192.168.3.0 mask 255.255.255.0               Advertises R3's LAN into
                                                    BGP — using an EXACT,
                                                    regular subnet mask (not a
                                                    wildcard), since BGP
                                                    requires the advertised
                                                    network to exactly match an
                                                    existing routing-table entry.
 network 192.168.4.0 mask 255.255.255.0               Also advertises R4's LAN
                                                    (learned into R3's own
                                                    routing table via EIGRP) —
                                                    the border router can
                                                    advertise routes it learned
                                                    from an IGP into BGP this
                                                    way.

==================================================

---------------- Confirm the problem (PC1) ----------------

Command                    Result
-----------------------------------------------------------------------------------------

---------------- Diagnose (R4) ----------------

Command                Result / Explanation
-----------------------------------------------------------------------------------------

Command                                    Explanation
-----------------------------------------------------------------------------------------

 address>                                  R3, giving R4 a path to reach
                                            anything beyond R3 — including
                                            Enterprise A's network, reached via

---------------- Verify (PC1) ----------------

Command                Result
-----------------------------------------------------------------------------------------

==================================================
CONCEPTS LEARNED
==================================================

• Combining independent routing domains under one lab — this lab
  demonstrates that OSPF (Enterprise A), EIGRP (Enterprise B), and BGP
  (Enterprise B's ISP connection) can all coexist in the same overall
  network without conflict, each confined to its own appropriate scope
  (an IGP within an enterprise, BGP at the boundary to another
  organization).
• GRE tunnel + OSPF combination (reviewed) — a tunnel interface
  included in an IGP's `network` statement lets two sites exchange
  routes as if directly connected, even though the physical path
  between them crosses an entirely separate network (here, the shared
  Internet/ISP cloud).
• Static default route vs. BGP for Internet connectivity — this lab
  deliberately contrasts the two approaches side by side: Enterprise A
  uses simple static routes (adequate for many real single-homed
  Internet connections), while Enterprise B specifically uses BGP
  instead, even though a static route would technically have worked
  just as well for its needs.
• Advertising IGP-learned routes into BGP without redistribution — R3
  manually advertises both its own LAN and R4's LAN (which R3 itself
  only knows about via EIGRP) into BGP using individual `network`
  statements — a simpler, more manual alternative to configuring true
  redistribution between EIGRP and BGP, appropriate for a small,
  stable network like this one.
• Recognizing when a simple static route is the right fix — R4 missing
  a route back to Enterprise A could have been solved with iBGP or
  EIGRP-to-BGP redistribution, but the lab deliberately chooses the
  simplest working solution (a static default route) instead,
  reinforcing that the "most advanced" solution isn't always the
  appropriate one for a given network's actual complexity.

==================================================
STUDY NOTES, EXAM SCENARIOS & REAL-WORLD CONTEXT
==================================================

Static routing vs. BGP for single-homed Internet connectivity
  Both are valid; the choice is architectural, not purely technical
  necessity.
  Exam: know that a simple static (often default) route is entirely
  sufficient and common for a single-homed Internet connection — BGP
  becomes necessary specifically for multi-homed connectivity (multiple
  ISPs) or when an organization needs to announce its own address
  space to the wider Internet, neither of which applies to Enterprise
  A here.
  Real world: this exact distinction — static routing for simple
  single-ISP connectivity, BGP reserved for more complex multi-homed or
  address-space-announcing scenarios — mirrors real-world network
  design decisions almost exactly.

Manually advertising IGP routes into BGP vs. true redistribution
  A small, deliberate design choice suited to a small, stable network.
  Exam: recognize that hand-typing individual `network` statements for
  every route to advertise (as done here) is a valid, simpler
  alternative to configuring `redistribute eigrp <as>` into BGP — but
  doesn't automatically track future changes to the IGP's routes the
  way true redistribution would.
  Real world: manual advertisement like this is realistic for a small,
  rarely-changing network; any organization with a growing or
  frequently-changing internal network would move to proper
  redistribution (with appropriate route filtering/route-maps) instead,
  to avoid needing to remember to update BGP every time an internal
  subnet changes.

Choosing the simplest working fix over a more "correct" one
  This lab explicitly acknowledges iBGP or redistribution would be the
  more typical/scalable fix, but deliberately picks a static route
  instead, since those techniques are out of scope.
  Exam: for CCNA-level troubleshooting, always reach for the simplest
  solution that satisfies the stated requirement — over-engineering a
  fix beyond what's actually being tested is its own kind of mistake.
  Real world: this reflects a genuinely important professional
  instinct too — a working static route shipped today is often better
  than a "more correct" but more complex solution that takes
  significantly longer to design and test, especially in a small,
  stable network where the added complexity of redistribution or iBGP
  wouldn't provide meaningful benefit.
