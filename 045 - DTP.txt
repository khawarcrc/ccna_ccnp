==================================================
STEP 1 - EXAMINE DTP, THEN DISABLE IT AND MANUALLY SET TRUNK/ACCESS MODE
==================================================

DTP (Dynamic Trunking Protocol) can automatically negotiate whether a
switch port becomes a trunk or stays an access port, based on the mode
of the port on the other end. This is convenient but a security risk in
production (an attacker could negotiate an unauthorized trunk), so best
practice is to always disable it and set port mode explicitly.

---------------- SW1 ----------------

Command                            Result / Explanation
-----------------------------------------------------------------------------------------
enable
show interface GigabitEthernet0/2  With no configuration yet, DTP is enabled by
 switchport                        default and the port shows "dynamic auto" mode
                                   — it will become a trunk only if connected to a
                                   port in trunk or "dynamic desirable" mode, but
                                   otherwise stays access.
configure terminal
interface GigabitEthernet0/2
 switchport mode dynamic ?          Reviewing the DTP mode options: `auto` becomes
                                    a trunk only if the far end actively negotiates
                                    one; `desirable` actively tries to form a trunk
                                    with a far end in either `auto` or `desirable`
                                    mode.

Rather than rely on any DTP mode, DTP is disabled and the mode set
manually on every port in use.

Command                            Explanation
-----------------------------------------------------------------------------------------
interface GigabitEthernet0/2        The trunk link to SW2.
 switchport mode trunk               Manually forces trunk mode.
 switchport nonegotiate               Disables DTP on this port — it will neither
                                     send nor respond to DTP negotiation frames.
interface GigabitEthernet0/1        The trunk link to R1 (needed for inter-VLAN
                                    routing).
 switchport mode trunk
 switchport nonegotiate
interface range FastEthernet0/1-2   The two PC-facing access ports.
 switchport mode access
 switchport nonegotiate             DTP is disabled here too, even on access
                                    ports, as a general best practice.
exit

---------------- SW2 ----------------

On enabling, SW2 logs: "%SPANTREE-2-BLOCK_PVID_PEER: Blocking
GigabitEthernet0/1 on VLAN0001. Inconsistent port type." SW1's G0/2 is
already forced into trunk mode, but because DTP is disabled on SW1's
end, no negotiation frames reach SW2 — so SW2's still-dynamic G0/1
interface never becomes a trunk on its own, leaving one end a trunk and
the other an access port: an inconsistent port type that blocks the
link until resolved.

Command                            Explanation
-----------------------------------------------------------------------------------------
enable
configure terminal
interface GigabitEthernet0/1        The trunk link to SW1.
 switchport mode trunk               Manually matches SW1's forced trunk mode,
                                     resolving the inconsistency.
 switchport nonegotiate
interface range FastEthernet0/1-2   The two PC-facing access ports.
 switchport mode access
 switchport nonegotiate

==================================================
CONCEPTS LEARNED
==================================================

• DTP (Dynamic Trunking Protocol) — a Cisco protocol that lets two
  connected switch ports automatically negotiate whether to become a
  trunk, based on each port's configured DTP mode (`auto`, `desirable`,
  `trunk`, or `access`). Convenient by default, but a security
  best practice is to disable it everywhere and set trunk/access mode
  manually, since an attacker could otherwise negotiate an unauthorized
  trunk port.
• `switchport mode dynamic auto` / `dynamic desirable` — the two DTP
  negotiation modes: `auto` only becomes a trunk if the far end actively
  requests one; `desirable` actively tries to form a trunk regardless of
  what the far end is doing (as long as the far end is `auto` or
  `desirable` too).
• `switchport nonegotiate` — disables DTP frame transmission/response on
  a port entirely, so its trunk/access mode is fixed exactly as
  configured and never changes based on the far end's behavior.
• Trunk port-type inconsistency — occurs when one end of a link is a
  trunk and the other is an access port (or otherwise mismatched trunk
  encapsulation/native VLAN); the switch detects this and blocks the
  port rather than passing traffic incorrectly, logging a
  "%SPANTREE...inconsistent port type" style message.
• Router-on-a-stick — a single physical router interface split into
  multiple logical subinterfaces (one per VLAN) using
  `encapsulation dot1Q <vlan-id>`, allowing one physical link to a
  switch trunk to perform inter-VLAN routing for every VLAN carried on
  that trunk, instead of needing one physical interface per VLAN.

==================================================
STUDY NOTES, EXAM SCENARIOS & REAL-WORLD CONTEXT
==================================================

DTP and `switchport nonegotiate`
  DTP negotiates trunk status automatically; `nonegotiate` disables that
  negotiation, forcing whatever mode is explicitly configured.
  Exam: know that leaving DTP enabled (default `dynamic auto` on most
  platforms) on an access port facing an end-user device is a real
  vulnerability — a rogue device could send DTP frames and negotiate
  itself into a trunk, gaining access to every VLAN on that trunk
  (a "VLAN hopping" style attack vector); `switchport mode access` +
  `switchport nonegotiate` closes it.
  Real world: disabling DTP on every access port is standard hardening
  practice in real switch deployments — this lab's "always disable it"
  advice reflects genuine production guidance, not just exam trivia.

Port-type inconsistency from asymmetric negotiation
  Forcing one end to trunk while disabling negotiation, without matching
  the other end, breaks the link rather than silently misbehaving.
  Exam: expect a scenario question where a newly-forced trunk "isn't
  working" — the fix is confirming both ends agree on trunk mode, since
  `show interfaces trunk` will simply not list a port stuck in this
  inconsistent state.
  Real world: this exact symptom appears whenever one side of a link is
  reconfigured without coordinating the change with whoever manages the
  other end — a common real-world cause of "the link just went down"
  tickets after a partial network change.

Router-on-a-stick with `encapsulation dot1Q`
  One physical interface, multiple logical subinterfaces, one per VLAN.
  Exam: know the physical interface itself typically carries no IP
  address in this design — only the subinterfaces do — and that the
  trunk carrying multiple VLANs to this router must allow every VLAN
  the router needs to route for.
  Real world: router-on-a-stick is common in smaller networks/branch
  offices where a single router (rather than a dedicated Layer 3
  switch) handles inter-VLAN routing — cost-effective, but the single
  physical link becomes a bandwidth bottleneck for all inter-VLAN
  traffic combined, which is exactly why larger networks move this
  function onto a Layer 3 switch instead.
