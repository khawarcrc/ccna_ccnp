Lab 070 - HSRP Troubleshooting

==================================================
LAB OBJECTIVE
==================================================

Troubleshoot two misconfigurations across the HSRP setup from Lab 069
(HSRP): a mismatched HSRP version between R1 and R2 on VLAN 10, causing
a duplicate-address condition (both routers claiming to be active), and
preemption left disabled on R2 for VLAN 20, meaning R2 never reclaims
its active role after recovering from a failure.

==================================================
TOPOLOGY
==================================================

Same topology as Lab 069 — see [hsrp.txt](hsrp.txt) for the full
diagram and addressing: two HSRP groups (group 10 for VLAN 10, virtual
IP 10.10.10.1, R1 normally active; group 20 for VLAN 20, virtual IP
10.20.20.1, R2 normally active). Nothing physically changed — one HSRP
configuration problem per VLAN group was introduced (both, in this
case, ended up being investigated on both routers before the actual
fault was found).

==================================================
PROBLEM 1 - VLAN 10: HSRP VERSION MISMATCH CAUSING A DUPLICATE ADDRESS
==================================================

---------------- Diagnose (R1) ----------------

Command                    Result / Explanation
-----------------------------------------------------------------------------------------
                              R1 is repeatedly logging the same error message:
                             "duplicate address 10.10.10.1" — the VLAN 10 virtual
                             IP. This specific error typically means the two
                             routers configured as an active/standby pair aren't
                             recognizing each other correctly, so BOTH end up
                             believing they're the active router — resulting in

                             10 — confirming the duplicate-active condition

                                        R2 and resolving the mismatch.

stopped on both routers — `terminal monitor` was re-enabled on each to
resume normal syslog display.

==================================================
PROBLEM 2 - VLAN 20: R2 (ACTIVE) NOT RECLAIMING ITS ROLE AFTER RECOVERY
==================================================

Per the lab instructions, R2 was observed to not retake its active role
for VLAN 20 after recovering from a simulated failure.

---------------- Diagnose (R2) ----------------

Command                            Result / Explanation
-----------------------------------------------------------------------------------------
show standby GigabitEthernet0/1      Confirms R2 is currently the active router
                                    for group 20 (fine, in its normal state) —
                                    but the described symptom (not reclaiming
                                    active status after recovering from a
                                    failure) is immediately recognizable without
                                    needing further investigation: this is
                                    specifically what happens when preemption is
                                    disabled. Sure enough, the output explicitly
                                    shows "Preemption disabled." With preemption
                                    off, a router that fails over to standby
                                    stays standby permanently even after
                                    recovering — it will only become active
                                    again if the CURRENT active router itself
                                    later fails.

---------------- Fix (R2) ----------------

Command                                Explanation
-----------------------------------------------------------------------------------------
configure terminal
interface GigabitEthernet0/1
 standby 20 preempt                      Enables preemption for group 20 on R2 —
                                        the lab's design instructions call for
                                        preemption to be enabled here, matching
                                        the intended behavior from Lab 069 (R2
                                        should reclaim active status after
                                        recovering).

---------------- Verify ----------------

Command                        Result
-----------------------------------------------------------------------------------------
show standby GigabitEthernet0/1  Confirms "Preemption enabled."

LAB SUMMARY

==================================================
CONCEPTS LEARNED
==================================================

• "Duplicate address" HSRP error — a specific, recognizable error
  message indicating two routers configured for the same HSRP group are
  both claiming to be active simultaneously, almost always caused by a
  configuration mismatch (like a version mismatch) preventing them from
  properly negotiating which one should actually be active.
• HSRP version mismatch as a root cause — routers running different
  HSRP versions (v1 vs. v2) on the same group don't correctly recognize
  each other's HSRP messages, leading directly to the duplicate-active
  condition; both routers' individual configurations can look
  reasonable in isolation, requiring a side-by-side comparison
  (specifically checking version) to spot the actual mismatch.
• `terminal no monitor` / `terminal monitor` — controls whether syslog/
  debug messages continue to display on the current console session;
  useful purely as a troubleshooting convenience when repeating
  messages make the terminal hard to work in, with no effect on the
  underlying configuration or problem itself.
• Preemption-disabled symptom recognition — "the active router doesn't
  reclaim its role after recovering from a failure" is such a specific,
  singular symptom of disabled preemption that it can often be
  diagnosed directly from the description alone, without needing
  extensive investigation — `show standby` explicitly reporting
  "Preemption disabled/enabled" is the direct confirmation either way.
• Symptom-first pattern recognition in troubleshooting — this lab
  demonstrates that experience with a protocol's specific, well-known
  failure symptoms (like this preemption case) can shortcut
  troubleshooting significantly, though it's still good practice to
  confirm the diagnosis with an actual `show` command rather than
  acting purely on assumption.

==================================================
STUDY NOTES, EXAM SCENARIOS & REAL-WORLD CONTEXT
==================================================

HSRP "duplicate address" from a version mismatch
  A specific, named error tied to a specific, common root cause.
  Exam: know that HSRP version mismatches (and similarly, mismatched
  group numbers or virtual IPs between what should be a paired
  active/standby configuration) are a classic cause of both routers
  believing themselves active — always compare BOTH routers'
  configuration side by side when this symptom appears, not just one.
  Real world: this exact error and root cause pairing is genuinely
  common in real HSRP deployments, especially after a router
  replacement/upgrade where the new device defaults to a different
  HSRP version than its still-in-service partner — a strong argument
  for explicitly configuring (not relying on defaults for) HSRP version
  on every device in a pair.

Preemption-disabled as an instantly-recognizable symptom
  "Doesn't reclaim its role after recovering" has essentially one cause.
  Exam: this exact phrasing/scenario, tied specifically to preemption,
  is a frequently tested pairing — expect to recognize it immediately
  rather than needing to work through a broader troubleshooting process.
  Real world: this is a genuinely common real-world "gotcha" —
  preemption being left at its default (disabled, in HSRP's actual
  default) after a maintenance window or router swap can leave the
  "backup" router permanently handling production traffic without
  anyone immediately noticing, until it's specifically checked.

`terminal no monitor` as a pure troubleshooting convenience
  Doesn't fix anything — purely manages console readability while
  investigating a separate real fault.
  Exam: don't mistake this for a configuration command relevant to the
  actual HSRP problem — it's unrelated to HSRP itself, just a general
  IOS console-management tool useful whenever debug/syslog output is
  making a terminal session hard to read.
  Real world: exactly the kind of small, practical habit experienced
  engineers use constantly during live troubleshooting sessions,
  especially on a device that's actively logging a recurring error —
  worth remembering as a general technique, not something specific to
  HSRP.
