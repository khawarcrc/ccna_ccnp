Lab 046 - VTP (VLAN Trunking Protocol)

==================================================
LAB OBJECTIVE
==================================================

Configure VTP (VLAN Trunking Protocol) across three switches to
propagate VLAN configuration from a single VTP server instead of
manually creating identical VLANs on every switch. Configure SW1 as a
VTP server, SW2 as VTP transparent, and SW3 as a VTP client, all in
domain "CCNA" running VTP version 2. Assign every access port to its
correct VLAN, and finish by restricting each trunk's allowed VLANs to
only the ones that actually need to cross it.

SW1 (VTP server) sits at one end of a three-switch chain, SW3 (VTP
client) at the other, with SW2 (VTP transparent) in the middle relaying
VTP advertisements between them without adopting them itself. PC1/PC2
(VLAN 10) and PC8 (VLAN 20) connect to SW1; PC3/PC4 (VLAN 40, local to
SW2 only) connect to SW2; PC5 (VLAN 10), PC6/PC7 (VLAN 30), and PC9
(VLAN 20) connect to SW3. VLANs 10 and 20 exist on both SW1 and SW3, so
they must cross both trunks — VLANs 30 and 40 each live entirely on one
switch and never need to cross a trunk at all, which is exactly why the
final allowed-VLAN restriction (1, 10, 20 only) doesn't break anything.

==================================================
STEP 2 - CONFIGURE SW2 AS VTP TRANSPARENT AND CREATE ITS LOCAL VLAN
==================================================

VTP has three modes: **server** (can create/delete VLANs and
advertises them to other switches), **client** (cannot create/delete
VLANs, only synchronizes what a server advertises), and
**transparent** (does not synchronize VLANs from a server at all, but
still forwards/relays VTP advertisement frames between other switches
— and can create its own purely local VLANs).

---------------- SW2 ----------------

Command                        Explanation
-----------------------------------------------------------------------------------------
vtp mode transparent            Configures SW2 as VTP transparent — it will
                                relay VTP messages between SW1 and SW3 without
                                adopting SW1's advertised VLANs itself.
vtp domain CCNA                 Sets the VTP domain name.
vtp version 2                   Sets VTP version 2 (Cisco recommends avoiding
                                version 1 where possible).
vlan 40
 name accounting                Creates VLAN 40 locally on SW2 — since SW2 is
                                transparent, this VLAN is NOT advertised to or
                                synced with SW1/SW3, it exists only on SW2.
exit
show vlan brief                 Confirms VLAN 40 ("accounting") now exists on
                                SW2.

Command                                    Result / Explanation
-----------------------------------------------------------------------------------------
interface GigabitEthernet0/1

 switchport trunk allowed vlan 5,6,7,8       Entering a new plain list REPLACES the
show interfaces trunk                        previous one entirely — now 5-8.
 switchport trunk allowed vlan add 9         `add` appends to the current list —
show interfaces trunk                        now 5-9.
 switchport trunk allowed vlan remove 9      `remove` removes from the current
show interfaces trunk                        list — back to 5-8.
 switchport trunk allowed vlan all           `all` allows every VLAN (1-1005) —
show interfaces trunk                        confirmed as the full range.
 switchport trunk allowed vlan none          `none` allows no VLANs at all —
show interfaces trunk                        confirmed as an empty list.
 switchport trunk allowed vlan except 2      `except` allows every VLAN EXCEPT the
show interfaces trunk                        one(s) listed — confirmed as 1,
                                             3-1005.

                                                  forward VLANs 1 (default), 10

VLAN 30 (local to SW3 only) and VLAN 40 (local to SW2 only) are
deliberately left off every trunk's allowed list — since neither VLAN
has members on more than one switch, neither needs to cross a trunk at
all, so restricting the trunks this way causes no connectivity loss.

==================================================
CONCEPTS LEARNED
==================================================

• VTP (VLAN Trunking Protocol) — a Cisco protocol that propagates VLAN
  configuration (VLAN IDs and names) across multiple switches within
  the same VTP domain, so VLANs only need to be created/deleted on one
  switch (a server) instead of individually on every switch.
• VTP server mode — can create, modify, and delete VLANs, and
  advertises those changes to other switches in the same domain; the
  default VTP mode on most switches.
• VTP client mode — cannot create, modify, or delete VLANs locally;
  instead it synchronizes whatever VLAN database a VTP server in its
  domain advertises.
• VTP transparent mode — neither creates/advertises VLANs to be synced
  by others, nor syncs VLANs from a server itself; however, it still
  forwards (relays) VTP advertisement frames it receives, allowing a
  transparent switch to sit between a server and client without
  breaking VTP synchronization between them. A transparent switch can
  still create VLANs, but they remain purely local to it.
• VTP domain name and version auto-adoption — a switch with the default
  (null) VTP domain name automatically joins the domain name carried in
  the first VTP advertisement it receives; similarly, a VTP version 1
  switch that receives an advertisement from a version 2 switch will
  automatically upgrade itself to version 2, if the platform supports
  it.
• `switchport trunk allowed vlan` syntax — a plain VLAN list (e.g.
  `1,2,3`) REPLACES the entire current allowed list; `add`/`remove`
  modify the existing list incrementally; `all` allows every VLAN;
  `none` allows no VLANs; `except` allows every VLAN except the ones
  specified. Restricting a trunk's allowed VLANs to only what's
  actually needed limits unnecessary broadcast traffic and reduces
  the security exposure of VLANs that don't need to be reachable
  across that link.

==================================================
STUDY NOTES, EXAM SCENARIOS & REAL-WORLD CONTEXT
==================================================

VTP server / client / transparent modes
  Server creates and advertises; client only receives; transparent
  relays without adopting, and can hold local-only VLANs.
  Exam: a very frequently tested distinction — know specifically that
  transparent mode still passes VTP advertisements through (unlike a
  switch that isn't running VTP at all, or is in a different domain,
  which would break the chain), even though it doesn't adopt them.
  Real world: transparent mode is genuinely useful for a switch that
  needs its own unique local VLANs (e.g. a switch serving a department
  with special network needs) while still sitting in the physical path
  between other switches that do need to share a VTP domain.

VTP domain name / version auto-adoption on a "blank" switch
  A switch with no VTP domain configured silently joins whatever domain
  it first hears advertised.
  Exam: this is also a real risk worth knowing for the exam AND in
  practice — a brand-new switch with default VTP settings dropped into
  an existing network can be silently absorbed into an unintended VTP
  domain and, in VTP v1/v2 server mode with a higher revision number,
  could even overwrite the VLAN database of the whole domain (a classic
  VTP "revision number bomb" incident).
  Real world: this exact risk is why many real deployments either avoid
  VTP entirely in favor of manually configured VLANs, or are extremely
  careful to reset a switch's VTP configuration (`vtp mode transparent`
  temporarily, or clearing VLAN.dat) before connecting it to a
  production network.

`switchport trunk allowed vlan`
  Controls which VLANs are permitted to cross a specific trunk link,
  independent of which VLANs exist on the switch overall.
  Exam: know that a plain list REPLACES rather than adds to the
  existing list — using `add`/`remove` when you meant to set an
  absolute list (or vice versa) is an easy, commonly-tested mistake.
  Real world: restricting trunk-allowed VLANs to only what's actually
  needed on that specific link is standard practice for both broadcast
  domain hygiene and security — it's a lightweight extra layer that
  limits the blast radius of a misconfigured or compromised device on
  one VLAN reaching a link it has no legitimate reason to use.
