Lab 036 - DNS (Domain Name System)

==================================================
LAB OBJECTIVE
==================================================

Learn how DNS (Domain Name System) translates hostnames into IP addresses.
Set up a DHCP pool on R1 that hands PC1 an IP address, default gateway,
and DNS server; observe that name resolution fails until a DNS server is
assigned; then manually configure a switch (which does not get its
addressing via DHCP the same way) with a static default gateway and DNS
server so it can resolve names too.

==================================================
TOPOLOGY
==================================================

           192.168.1.0/24
  PC1 ----+                    Server1 (192.168.1.101)
  PC2 ----+------- R1 ---------Server2 (192.168.1.102)
  SW1 ----+                    DNS1    (192.168.1.100)

All devices sit on the same 192.168.1.0/24 subnet. R1 acts as the DHCP
server for the segment, handing addressing to **both PC1 and PC2** from
the same pool. DNS1 is a pre-built DNS server (not configured in this
lab) already holding hostname-to-IP records for Server1, Server2, and
the other networking devices.

==================================================

SW1 already has an IP address on its VLAN 1 interface, so it can send and

---------------- SW1 ----------------

Command                    Result

==================================================
CONCEPTS LEARNED
==================================================

• DNS (Domain Name System) — a distributed naming service that resolves
  human-readable hostnames (e.g. "server1") to the IP addresses computers
  actually use to communicate. Used here so PC1/SW1 can reach servers by
  name instead of memorizing their IP addresses.
• DHCP DNS-server option (`dns-server` inside `ip dhcp pool`) — a setting
  in a DHCP pool that tells the DHCP server to hand out a DNS server's
  address to clients, in the same lease as their IP address and default
  gateway, so the client needs no separate manual DNS configuration.
• Ping by IP address vs. ping by name — pinging an IP address is a
  connectivity test that never involves DNS; pinging a hostname first
  requires the device to resolve that name to an IP address via a DNS
  server, so it exercises both name resolution and connectivity at once.
• "Ping request could not find host <name>" — the specific IOS error
  returned when a device attempts to resolve a hostname but has no DNS
  server configured (or the DNS server itself is unreachable/has no
  record), as opposed to a routing/connectivity failure.
• Switch addressing vs. DHCP client behaviour — a switch's VLAN 1 (or any
  SVI) can hold an IP address without being a full DHCP client the way a
  PC is; that address alone does not carry a default gateway or DNS
  server, so both must be set explicitly.
• `ip default-gateway` — the global-configuration command that manually
  sets a Layer 2 switch's default gateway (the router it sends
  off-subnet/off-device traffic to), functionally equivalent to what a
  PC's DHCP lease provides automatically.
• `ip name-server` — the global-configuration command that manually sets
  the DNS server a switch itself uses to resolve hostnames, equivalent to
  the DNS server a PC receives via DHCP.

==================================================
STUDY NOTES, EXAM SCENARIOS & REAL-WORLD CONTEXT
==================================================

DNS (Domain Name System)
  Translates a hostname to an IP address. Doesn't affect IP-level
  connectivity at all — a device with no DNS server can still ping by IP,
  it just can't resolve names.
  Exam: know the failure message ("Ping request could not find host
  <name>") means no/failed DNS resolution, not a routing or connectivity
  problem — don't jump to checking the gateway when this is the symptom.
  Real world: this is the single most common "why won't it connect"
  ticket that turns out to be DNS, not the network — always confirm
  ping-by-IP works before troubleshooting anything else.

DHCP option 6 (`dns-server` in `ip dhcp pool`)
  DHCP can hand out a DNS server address alongside the IP/gateway, in the
  same DHCPOFFER/DHCPACK. No extra exchange needed.
  Exam: know `dns-server` is a line inside `ip dhcp pool`, same place as
  `default-router` — an easy one-word swap trap on exam questions.
  Real world: this is why plugging a laptop into any properly configured
  office network "just works" for both browsing and pinging internal
  hostnames, with zero manual configuration on the client.

Switch management IP has no DHCP-style gateway/DNS
  A switch's VLAN 1 (or any SVI) can get an IP address via `ip address
  dhcp`, but that alone does not give it a default gateway or DNS server
  the way a PC's DHCP lease does — those need `ip default-gateway` and
  `ip name-server` set explicitly.
  Exam: a classic exam trap — a switch with an IP but no
  `ip default-gateway` cannot be reached from, or reach, anything off its
  own subnet, and this command is easy to forget since routers/PCs don't
  need it stated as its own command.
  Real world: this is exactly why a freshly racked switch answers pings
  from its own subnet but can't be reached from the NOC or reach an NTP/
  syslog/TFTP server elsewhere — `ip default-gateway` (and `ip
  name-server` if it needs to resolve names itself, e.g. for `ntp server
  pool.ntp.org`) is one of the first things checked.
